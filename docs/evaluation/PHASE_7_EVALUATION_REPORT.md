## 1. Executive Summary

This phase built a real evaluation framework and ran it against a small,
honestly-scoped pilot benchmark. **Retrieval evaluation is real and
measured**: real BM25, real BGE-small dense embeddings + FAISS, real
Reciprocal Rank Fusion, and a real cross-encoder reranker were exercised
against 12 answerable pilot questions. **Generation, HyDE, and multimodal
(VLM/OCR/real transcription) evaluation are NOT MEASURED** — Ollama,
tesseract, and a real transcription/VLM run are not available in this
environment (see §4 "System Under Evaluation"). Every number in this
report is either measured, explicitly labeled as a mocked pipeline-
validation check (never used as a performance claim), or marked NOT
MEASURED — nothing is fabricated or estimated in its place.

Within retrieval, the ablation shows cross-encoder reranking
(`H_hybrid_rrf_reranked`) improving recall@5 over hybrid RRF alone
(`E_hybrid_rrf`) from 0.681 to 0.764 and precision@5 from 0.433 to 0.467,
at roughly 4.6× the per-query latency (8.9ms → 41.1ms mean). Neither
difference reaches statistical significance at this sample size (n=12);
see §26. A controlled chunking experiment (whitespace vs. real BGE
subword token counting) showed **no measurable difference** on this
corpus — every chunk is far under the 512-token target either way, so the
documented Phase 2 tokenization-inflation issue never actually triggers
here. This is reported as a negative/negligible result, not hidden.

## 19. Chunking Experiment (7F.2)

Controlled comparison, single variable (chunking's token-counting
function), all else held constant (hybrid RRF, top_k=5, same corpus):

| | C1 — whitespace count (existing) | C2 — real BGE subword count |
|---|---|---|
| MRR | 0.854 | 0.854 |
| Recall@5 | 0.681 | 0.681 |
| Precision@5 | 0.433 | 0.433 |
| nDCG@5 | 0.706 | 0.706 |

**No measurable difference.** Mean token-inflation ratio (real BGE tokens
÷ whitespace words) across this corpus's chunks was **2.19×** — confirming
the Phase 2-documented tokenization gap is real — but **zero** chunks in
this corpus exceed 512 BGE tokens even at that inflation rate, because the
underlying text runs are short (single-topic, ~9-13 chunks per document).
The chunking algorithm's *packing decisions* never actually differ between
C1 and C2 on this corpus, so retrieval quality cannot differ either.

**Conclusion: this experiment does not justify adopting BGE-token-aware
chunking on the current pilot corpus.** The underlying tokenization-gap
finding (2.19× inflation) is real and worth retaining as a known risk for
a larger/denser real corpus, where a whitespace-512-word chunk could
plausibly cross the true BGE limit — but that risk is not exercised here,
so `ChunkingConfig.token_counter` was added as an available, tested option
(§3) without being adopted as the new default. Full data:
`evaluation/results/run_baseline_20260904T032025Z/chunking_experiment.json`.

## 21. RRF Experiment (7F.4)

| Configuration | MRR | Recall@5 | nDCG@5 |
|---|---|---|---|
| A — BM25 only | 0.667 | 0.611 | 0.590 |
| B — Dense only | 0.806 | 0.708 | 0.685 |
| D — Simple score fusion (min-max normalize + sum) | 0.722 | 0.611 | 0.622 |
| E — RRF fusion (k=60) | 0.854 | 0.681 | 0.706 |

RRF (E) outperforms the naive score-sum baseline (D) on MRR (+0.132) and
nDCG@5 (+0.084), and matches or exceeds the stronger single retriever (B)
on MRR (+0.048) and nDCG@5 (+0.021), though not on Recall@5 (B: 0.708 vs
E: 0.681). This is consistent with — but on n=12 questions does not
statistically confirm — the standard justification for using RRF over
naively summing incomparable BM25/cosine scores.

## 23. Failure Analysis

`backend/app/benchmarking/failure_analysis.py` inspects every question
scoring recall@5 < 1.0 under `E_hybrid_rrf` and classifies the failure
using BM25-only/dense-only top-20 probes (the finest-grained diagnosis
possible without generation output — see the module docstring for why the
full 17-category taxonomy from the brief is not attempted here).

Result: **8 of 12 answerable questions failed** (recall@5 < 1.0), **all 8**
classified `chunk_boundary_or_ranking_problem` — the gold chunk was found
by *both* BM25 and dense retrieval within their own top-20, but did not
survive to the final top-5 after RRF fusion.

**This classification result is itself a documented limitation, not a
strong finding**: the pilot corpus has only 23 chunks total, so a top-20
probe pool contains nearly the entire corpus for both retrievers by
construction — "found in top 20" is a weak signal here and would be far
more discriminating on a corpus of hundreds or thousands of chunks. The
practical, actionable version of this finding is simply: **on this small
corpus, most retrieval misses are ranking-order problems, not lexical or
semantic retrievability problems** — which is exactly the class of problem
cross-encoder reranking is designed to fix, and §10/§22 show it measurably
does (recall@5 0.681 → 0.764).

The one failure not improved by reranking: `p011` (the image/diagram
question) scored recall@5 = 0.333 under both E and H — its gold chunks
(an empty `IMAGE` chunk plus an "organelle diagram" caption chunk) are
short, generic text that neither lexical nor dense retrieval, nor
reranking, distinguishes well from the surrounding table/photosynthesis
content. This is a real, inspectable multimodal-retrieval limitation of
the current architecture (no VLM description to retrieve against — see
§17), not noise.

## 24. Evidence-Based Improvements

**Problem:** §23 shows 8/12 (67%) of retrieval misses on this benchmark
are ranking-order problems (both retrievers found the gold chunk, but it
didn't survive to the top-5), not retrievability problems.

**Evidence:** §10/§22 — cross-encoder reranking (`H`) measurably improves
recall@5 (0.681→0.764, +12.2%) and precision@5 (0.433→0.467, +7.7%) over
hybrid RRF alone (`E`) on exactly this benchmark.

**Hypothesis:** Reranking the fused candidate pool with a cross-encoder
fixes ranking-order errors without changing what's retrievable, so making
it the default retrieval configuration (rather than an optional/research
mode) should improve real answer quality once generation is available.

**Implementation:** No core code change was required — cross-encoder
reranking already exists in this codebase
(`app/retrieval/reranker.py`, `CrossEncoderReranker`) and was already
exercised as part of `RetrievalService.full_baseline`. The Phase 7H
"implementation" is the recommendation itself: **use hybrid RRF + reranker
(without requiring HyDE, since HyDE is unavailable) as the default
retrieval configuration**, which is exactly what `H_hybrid_rrf_reranked`
in `app/benchmarking/configurations.py` composes. This is a configuration
recommendation, not a new algorithm.

**A second candidate improvement — BGE-token-aware chunking — was
evaluated (§19) and *not* adopted**, because the controlled experiment
found no measurable benefit on this corpus. This is reported as required
by the brief ("if it performs worse or has negligible benefit, document
that too"), not omitted because it was a negative result.

**Result:** See §25/§26 for the baseline-vs-final comparison and its
statistical caveats. The directional improvement is real and measured;
it is not claimed to be statistically confirmed at this sample size.

## 26. Statistical Analysis

**Test used:** paired Wilcoxon signed-rank test
(`app/benchmarking/statistics_.py::paired_wilcoxon`), computed per-question
between E and H on each metric. Chosen over a paired t-test because
per-query metric values are bounded in [0,1] and not approximately normal,
and the sample is small (n=12).

**Sample size:** 12 answerable questions — small, and explicitly noted as
limiting statistical power (only a handful of the 12 pairs actually differ
between E and H for most metrics).

| Metric | p-value | Significant at α=0.05? |
|---|---|---|
| reciprocal_rank | 0.750 | No |
| recall_at_5 | 0.250 | No |
| precision_at_5 | 0.500 | No |
| ndcg_at_5 | 1.000 | No |
| hit_rate_at_5 | N/A (no pairs differ) | No |

**None of the observed differences reach statistical significance at
this sample size.** The directional findings in §24/§25 should be read as
"consistent with reranking helping, worth adopting given it costs no new
implementation" rather than "statistically proven to help." A larger
question set (the 7B-2/7B-3 scale-up noted in DATASET.md as blocked on
real corpus availability) is required before a stronger claim would be
justified. Full test output:
`evaluation/results/run_baseline_20260904T032025Z/statistical_analysis.json`.

## 27. Latency / Efficiency

Measured on this run's hardware only (see manifest `platform` field —
macOS/Apple Silicon, CPU-only, no GPU):

| Configuration | Mean (ms) | Median (ms) | P95 (ms) | n |
|---|---|---|---|---|
| E — Hybrid RRF (no reranker) | 8.9 | 9.0 | 9.7 | 12 |
| H — Hybrid RRF + reranker | 41.1 | 40.6 | 42.7 | 12 |

Reranking costs approximately **+32ms mean per query** (≈4.6×) on this
23-chunk corpus, CPU-only. This is not comparable to latency on a larger
corpus or GPU-backed hardware and should not be extrapolated as such.
Ingestion/embedding/index-build latency was not separately isolated in
this run (it happens once per stack build, not per query) and is not
reported as a per-query figure. Generation latency: **NOT MEASURED** (no
generation was run).

## 28. Limitations

- Single-subject, 23-chunk pilot corpus (§5/DATASET.md) — all quantitative
  findings above should be read as pipeline validation with directionally
  informative numbers, not as claims that generalize to a larger or more
  diverse corpus.
- Generation, faithfulness, citation validity, token grounding on live
  output, evidence-sufficiency/abstention decisions, contradiction
  detection, and real multimodal (VLM/OCR/transcription) evaluation are
  all NOT MEASURED — no local LLM/Ollama, tesseract, or real
  transcription/VLM run was available in this environment.
- HyDE is only pipeline-validated with a mocked query expander (§18); its
  real effect on retrieval quality is unknown.
- Statistical significance was not established for any measured
  improvement (§26) — sample size is the limiting factor.
- Failure-category attribution (§23) is coarsened by the corpus's small
  size (a top-20 probe covers nearly the whole corpus).
- Latency figures are CPU-only, single-machine, and not meant for
  cross-hardware comparison.

## 30. Conclusions

Under the evaluated dataset and configuration, hybrid RRF retrieval
(BM25+BGE-small, RRF k=60) performs competitively with either retriever
alone, and cross-encoder reranking on top of it shows a directionally
positive effect on recall@5 and precision@5 at a measured latency cost —
though not a statistically confirmed one at this sample size. A
controlled chunking experiment found no benefit to BGE-token-aware
chunking on this particular corpus, despite confirming the underlying
whitespace/BGE-token inflation ratio (2.19×) that motivated testing it.
Generation-dependent evaluation (faithfulness, citations, grounding,
abstention, contradiction, real multimodal retrieval) could not be run in
this environment and is explicitly reported as not measured rather than
estimated. This should be read as a validated evaluation *framework* with
a small, honest first dataset — not as a comprehensive benchmark of the
full EduRAG-inspired architecture.

## 31. Future Work

- Add real multi-subject academic material to `data/raw/` and extend
  `pilot_v1` toward the 7B-2/7B-3 scale (200-500 questions across 5-10
  subjects) using the same never-hand-typed chunk-id discipline.
- Install Ollama + `deepseek-r1:8b` (and optionally `llava-phi3`) to
  unblock generation, faithfulness, citation, token-grounding, abstention,
  and contradiction measurement (§11-16), and re-run this same benchmark
  with generation-dependent metrics filled in.
- Install `tesseract` and run real (non-mocked) transcription to unblock
  real multimodal evaluation (§17).
- Re-run the chunking experiment (§19) once a larger/denser real corpus
  exists, where the 2.19× token-inflation ratio is more likely to actually
  push a chunk over the 512-BGE-token limit.
- Re-run the reranker/RRF ablations (§21-22) at a larger sample size to
  obtain a statistically meaningful significance test (§26).
